OmO Memory — Dream, People, Soul

2026-10-04

OmO's memory subsystem is one configuration block with three sections that do different jobs. memory.soul is the model the agent holds of itself. memory.people is the model it holds of the humans it works with. memory.dream is the background run that maintains both while nobody is watching. Two of the three have tips; the third is only visible in the persona text and in the /sleeptime output.

Everything below was read from the installed code, not from documentation: the plugin bundle at ~/.omo/binary-runtime/<version>/plugin/extensions/omo.js (schemas, defaults, gates, renderers), plugin/extensions/dream-persona.md (the dream run's contract), and the senpi package's tip catalog at <senpi>/dist/modes/interactive/tips/.

Soul — the self-model

The system/ directory is the always-in-context part of memory. Every prompt is rebuilt from it: the projection builder emits <projection>$MEMORY_DIR/system/persona.md</projection> and the file body inside a <self> block, with human.md, boundaries.md and self-aware.md following in a <memory> block. Every other file in the repo appears only as a name inside <external_projection>; its body is never injected.

  • system/persona.md — the agent's own description of itself, and the only file whose edits always get announced.
  • system/identity.md — optional, four lines, and never seeded: created only when a real identity has emerged.
  • system/boundaries.md — the user's exact words about what not to do.
  • system/human.md, system/self-aware.md — the person card for the primary human, and the outside view of the agent's own behaviour.

Three paths form the guarded set: system/persona.md, system/identity.md, system/boundaries.md. A memory write touching any of them changes the tool result it returns — the text "This was a soul edit: announce it to the user in your reply." is appended — and emits an omo-memory:soul-updated message, drawn in the transcript as a "Remembered about myself" notice naming the file, the commit sha and the subject. The gate is memory.soul.edit_notice, on by default; memory.agents.<id>.soul.edit_notice overrides it per identity. A soul-head.json watermark under the notice lock keeps one edit from being announced twice.

The doctor command also carries a soul-seed check: it sha256s the persona and compares it against the shipped v1 seed hash (ed910679…c0e8e). If they still match, it warns that the file is the untouched seed and should be rewritten against the newer seed.

People — the person model

People knowledge lives in two layers, and the split is enforced by who is allowed to write where. A card holds what is stable about a person; an observation ledger holds what was noticed and when. The primary human's card is system/human.md; everyone else gets people/<slug>/card.md plus people/<slug>/observations.md.

Cards are parsed, not free text. Every line carries one of four prefixes — IDENTITY, ATTRIBUTE, RELATIONSHIP, INSTRUCTION — and a RELATIONSHIP line must read <predicate>: <target-slug>. Those lines become nodes and edges, which is what the /people roster and relationship graph are drawn from; a malformed edge is reported rather than dropped.

Observation ledgers are split into four sections: Explicit, Deductive, Inductive, Contradiction. Authorship is deliberately lopsided:

  • Explicit is written only by the facts extractor.
  • Deductive, Inductive and Contradiction are written only by a dream run.
  • A deduction must cite the observation lines it rests on. An induction states the pattern and a confidence level, and never touches a card. A contradiction is flagged status: open and is never resolved by the machine.

The limits are configuration, not convention: people.max_entries (default 40, bounds 1-100) and people.max_entry_chars (default 200, bounds 50-500). The gate is people.enabled; with it off, /people answers "people records are disabled (memory.people.enabled)". The command itself is /people [<name>] [--all] [--ask "<question>"] — roster and graph, one card with its observations, or a read-only answer over that person's record.

Dream — the consolidation run

A dream is not a reflection. A reflection captures one stretch of conversation; a dream works across the whole memory filesystem and many conversations at once. Its contract lives in plugin/extensions/dream-persona.md and runs in six ordered phases: investigate, consolidate, audit skills, maintain people, review, commit. Every run that changes something ends in a git commit stamped Omo-Writer: dream.

What a run actually does:

  • Dedupe. One home per fact. The best-worded copy survives, the others go, and a [[path]] cross-reference is left where a reader would still look.
  • Tier rebalance. A file the agent keeps fetching is promoted into system/; a system/ file nothing recent needed is demoted to reference/ — moved, never deleted. The usage ledger is the evidence, not a hunch.
  • Archiving. Fact entries older than six months are summarized into ARCHIVE.md and the originals removed.
  • Skill audit. A skill that is merely unused becomes a report-only deprecation candidate; a skill that evidence shows to be wrong gets fixed in place.
  • People. The deduction, induction and contradiction work described above.
  • Token budget. If committed system/ is over compile_warn_tokens (default 30000), the run must finish under 80% of that budget, trimming the largest files first and self-aware.md before anything else.

Automatic dreams pass a four-step gate before they launch:

  1. enabled false — rejected.
  2. Origin is shutdown and shutdown_launch is false — rejected.
  3. The last dream ended within 3600000 × min_hours_between ms — rejected as too_soon.
  4. Origin is not pressure and unreflected conversation is at or below 8192 bytes — rejected as insufficient_volume.

With the defaults — idle_minutes: 30, min_hours_between: 24, shutdown_launch: true — that means a dream needs half an hour of idle, more than 8 KB of unreflected conversation, and a day since the last one. A run's origin is a validated enum, manual | idle | shutdown | pressure, and a throttled run parks rather than dying: it re-probes six hours after it parked.

Manual runs go through /dream [--auto | --recent N | --conversation <ids> | --from transcript:<path>] [--to <doc>] [focus], and bypass the idle and volume gates. Automatic selection caps at 5 conversations and 150000 characters per run. Each run works in a real git worktree of the memory repo — the run ledger records worktreeDir, worktreeBranch, baseSha and a snapshot of the repo's git state — and merges back on success. Between runs, state sits in runtime/dream/state.json.

Neighbours worth not confusing with these

  • nudge (every_user_turns: 10) asks the agent to write memory; Kibitzer or recall only reads it and surfaces a hint mid-task.
  • facts (debounce_settles: 4) is the explicit-fact extractor — the only writer of ## Explicit.
  • reflection condenses one conversation; dream condenses many, plus the whole repo.
  • people is the model of the human; soul is the model of the agent. Dream maintains both.
