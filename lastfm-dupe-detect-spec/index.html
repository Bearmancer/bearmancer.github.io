Spec: Surface Consecutive Duplicate Scrobbles

Repo: Toolbox. Implementation branch: omos/lastfm-dupe-detect (throwaway worktree). Status: ready-for-agent.

Problem Statement

The Last.fm history contains back-to-back repeats — the same track played twice in a row — but the dashboard never shows them. A read-only probe of the full history found 1,326 adjacent pairs whose normalized track title, artist, and album match, yet a person has to run an ad-hoc SQL query by hand to see any of them. The dashboard's Last.fm tab lists scrobbles but has no notion of a repeat, so the signal is invisible.

Solution

The dashboard gains a Repeats view. When the dashboard is generated, the scrobble list is scanned once for adjacent pairs that share a normalized triple, and the resulting pairs are exported to the page like the other Last.fm data. The browser renders them in a table — earlier play, later repeat, track, artist, album — searchable with the same shared search the other tables use. No sync change, no schema change, no new dependency.

User Stories

  1. As the dashboard owner, I want a view that lists every back-to-back repeat, so that I can see what I replay without writing SQL.
  2. As the dashboard owner, I want each row to show the earlier play and the later repeat with full date and time, so that I can tell exactly when the repeat happened.
  3. As the dashboard owner, I want the track, artist, and album on each row, so that I can identify the recording.
  4. As the dashboard owner, I want the list ordered newest repeat first, so that recent habits are at the top.
  5. As the dashboard owner, I want case and surrounding whitespace to not create false repeats, so that "Foo" and "foo " are treated as one track.
  6. As the dashboard owner, I want a blank album to compare equal to another blank album, so that singles without album metadata still match.
  7. As the dashboard owner, I want the same track separated by a different track to not count as a repeat, so that only true adjacent repeats appear.
  8. As the dashboard owner, I want the Repeats view to load without slowing first paint, so that the dashboard stays fast.
  9. As the dashboard owner, I want to search and filter the Repeats table, so that I can find repeats of a particular artist or track.
  10. As the dashboard owner, I want the repeats computed at dashboard generation time, so that the view is always current with the synced history.
  11. As the dashboard owner, I want the feature to work offline over the local file, so that no network call is needed to show repeats.
  12. As a maintainer, I want the detection to be a pure function over the scrobble list, so that it is testable without a database or browser.
  13. As a maintainer, I want the detection to follow the existing export-and-render split, so that no HTML is built in C#.
  14. As a maintainer, I want no change to the sync pipeline, so that the upsert path stays simple.
  15. As a maintainer, I want the payload to reuse the column-array shape used by the full scrobble export, so that large histories stay small on the wire.

Implementation Decisions

  • Detection is a pure function over the already-materialized scrobble list, ordered newest-first. It walks adjacent rows and compares each with its predecessor.
  • Same means the normalized triple: track title, artist, and album each lowercased and trimmed, with a blank or missing album treated as one empty value. Case and surrounding whitespace never distinguish. Featured-artist tags and punctuation are literal — no splitting or stripping.
  • Home: a private static method on the existing dashboard orchestrator, alongside the other data-build methods. The codebase convention is one orchestrator with no single-caller helper classes, so no new class or interface is introduced.
  • Export: a new JS global for the pairs, written to its own file next to the existing Last.fm exports. The pair payload reuses the column-array shape (one array per field) that the full scrobble export uses, for payload size.
  • Render: a new Repeats view in the dashboard's client-side JS, built from the new global with the existing Tabulator setup and the shared search function. C# never builds HTML.
  • No schema change, no sync change. The sync step stays a plain upsert pipe.
  • Known caveat: the database lowercases ASCII only; exotic Unicode case differences could evade normalization. This matches the probe's semantics and is accepted.

Testing Decisions

  • A good test exercises the pure detection function on small in-memory lists and asserts the returned pairs; it does not touch the database or the browser.
  • Cases to cover: empty list, single row, two identical adjacent rows, the same track separated by another track (not a repeat), case and whitespace variants, blank-versus-blank album equality, blank-versus-populated album inequality, and newest-first ordering of the output.
  • Prior art: the existing pure-function tests in the Last.fm and Core test projects (for example the YouTube sort tests), which test functions directly without infrastructure.

Out of Scope

  • Changing the Last.fm sync pipeline or the scrobble schema.
  • Deduplicating or deleting repeats; the view is read-only.
  • Publishing repeats to the public GitHub Pages site (the bearmancer site already carries the full list separately).
  • Repeats spanning a non-adjacent gap (e.g. same track three plays apart).

Further Notes

The detection seam is the highest available: the scrobble list is already materialized in the orchestrator before any export is built, so detection adds no new I/O and no new seam. If the reviewer prefers the detection to live in the Last.fm service instead, that moves it below the existing seam and should be justified.
