Repeat Plays: Finding Consecutive Duplicate Scrobbles

Across 56,007 Last.fm scrobbles, 1,326 adjacent pairs are the same track played back to back — the same episode rewatched, the same live cut replayed. Nothing in the sync pipeline ever looked for them: scrobbles are stored keyed by timestamp and never compared with their neighbors, so repeats were invisible, not broken. A single read-only window query over the play history surfaces every one.

What Counts as the Same Track

Two consecutive rows count as the same when their normalized triple matches: lowercased, trimmed track title, artist, and album — with a blank or missing album treated as one empty value. Case and surrounding whitespace never distinguish tracks. Featured-artist tags, punctuation, and extra internal spaces are taken literally, never split or stripped.

How the Probe Works

The history table is ordered newest-first by play timestamp, each row is normalized, and every row is compared with its predecessor through a LAG window. No schema change, no new model, no application code: the database engine does the sort and the scan in one pass. A line-by-line cross-check over the same ordering reproduces the pairs on small samples, but the window query stays primary — it never materializes tens of thousands of rows into memory.

What the Data Showed

All 56,007 timestamps are distinct, so no two plays ever collided inside one second and no repeat was ever lost to a primary-key overwrite. 365 rows carry a blank album, covered by the empty-album rule. The 1,326 pairs are dominated by rewatched television — the same MacGruber episode three times in a row, repeated Abbott Elementary and Vice Principals episodes — plus replayed live tracks from Bowie to Tchaikovsky.

Ruling Out False Pairs

Four artifacts could fake a pair and were each excluded: same-second rows whose order is arbitrary (none exist here), pairs split across an incremental sync boundary (the probe reads the full table, not a slice), the now-playing entry that carries no timestamp and never enters the table, and single-track API responses that cannot form a pair. One caveat survives: the database lowercases ASCII only, so exotic Unicode case differences could slip past — no such rows observed.

Where This Belongs

If repeat detection ever becomes a permanent feature, it belongs in the dashboard layer after the scrobble list is loaded — not in the sync step, which should stay a plain upsert pipe. Until then the query is the feature: rerun it any time the history grows.
